# Accessibility audit report

**Website:** [Tamil Nadu Government Portal](https://www.tn.gov.in/)  
**Pages in scope:** home, Services and FAQ  
**Audit purpose:** identify practical barriers and record a repeatable baseline

## Why I chose this website

The portal is a starting point for people looking for Tamil Nadu Government information and services. Its FAQ describes it as a single-window source for state information. The FAQ also says that accessibility options such as font size and contrast controls are available at the top of the page.

That made it a useful site for this exercise: the service catalogue is large, and the portal itself makes a clear statement about accessibility support.

## How to read these findings

I have not treated every possible risk as a proven WCAG failure. Some items are observations about the amount and structure of content; others are checks that need to be judged from the live browser evidence. The Lighthouse report, keyboard trace and axe results generated by the workflow are the evidence to use when reviewing the findings.

## Findings and priorities

### 1. Make the service navigation easier to scan

**Priority: High**

The Services page groups a long list of departments, including Revenue, School Education, Transport and Social Welfare. That grouping is useful, but it also means a visitor has to move through a lot of choices before reaching the right service.

**Why it matters:** Someone who does not know which department owns a service may have trouble deciding where to start. A long list is also tiring to navigate with a keyboard or screen reader.

**Suggested improvement:** Keep the department groupings, but add a short introduction, a clear heading structure and a way to narrow the list. Link names should make sense when read outside the surrounding paragraph.

**Evidence:** [Services page](https://www.tn.gov.in/services.php). See the browser screenshots and accessibility scan saved alongside this report.

### 2. Make sure the promised accessibility controls are easy to find and use

**Priority: High**

The portal FAQ says that users can increase or decrease font size and switch colour/contrast schemes. That is a helpful commitment, but controls only help when people can find them and operate them with their own input method.

**Why it matters:** A control that only works with a mouse, has no accessible name or gives no indication of its state can be difficult to use.

**Suggested improvement:** Give each control a clear name, keyboard focus, and a predictable state. Check the controls at common zoom levels and on a small screen.

**Evidence:** [Official FAQ](https://www.tn.gov.in/faq.php), plus the FAQ page capture and keyboard trace in `docs/screenshots/` and `docs/audit/keyboard-results.md`.

### 3. Keep keyboard focus visible throughout navigation

**Priority: High**

A visitor may move from the main menu into service links, cards, forms and footer links. The focus indicator should remain easy to see at every step and should not disappear behind a fixed header or another element.

**Why it matters:** When someone cannot tell which item is focused, keyboard navigation becomes slow and error-prone.

**Suggested improvement:** Use a consistent high-contrast focus style and check it at different viewport sizes. Do not rely on colour alone to show focus.

**Evidence:** The recorded Tab/Shift+Tab sequence is in `docs/audit/keyboard-results.md`. The Lighthouse and axe outputs provide additional automated checks, but visual review is still useful.

### 4. Give the page a clear heading and landmark structure

**Priority: Medium**

The home page contains several content areas, including documents, contacts, press releases, forms and schemes. Clear headings and landmarks help visitors jump to the part they need rather than reading every section in order.

**Why it matters:** A person using a screen reader often navigates by headings and landmarks. Meaningful link text also helps when links are listed out of context.

**Suggested improvement:** Use one clear page heading, meaningful section headings and semantic navigation/main/footer landmarks. Avoid using a visual style as a substitute for heading markup.

**Evidence:** The Lighthouse/axe results in `docs/audit/lighthouse/` and `docs/audit/axe-results.json` show which automated checks reported issues on the pages tested.

### 5. Keep the demo application easy to change and test

**Priority: Medium**

The project uses a simple React client and Express server. The page calls an API; the server returns data from a separate service-list module. This is a deliberate boundary, even though the current data is stored in memory.

**Why it matters:** If a UI component also owns database queries, it becomes harder to test or replace the data source. Accessibility fixes can then become entangled with unrelated backend changes.

**Suggested improvement:** Keep the browser focused on presentation and interaction, keep HTTP routes in the server, and place future database access behind a repository module.

**Evidence:** The project tree and [architecture notes](../architecture/README.md) show the separation in this starter implementation.

## Priority summary

| Finding | Priority | Main action |
|---|---|---|
| Service navigation is lengthy | High | Improve grouping, headings and ways to narrow choices |
| Accessibility controls need an end-to-end check | High | Verify names, focus, state and keyboard operation |
| Focus must stay visible | High | Check the complete keyboard path at desktop and mobile sizes |
| Headings and landmarks should be clear | Medium | Use semantic structure and descriptive link names |
| Keep client/server responsibilities separate | Medium | Preserve the API and data-access boundary |

## What this audit does not claim

Lighthouse and axe can identify many code-level problems, but they cannot decide whether every service journey makes sense to a citizen. The keyboard script sends real Tab and Shift+Tab input in Chromium, but it is still an automated pass. It is not a substitute for a person testing with a screen reader, switch device or other assistive technology.

The report should be read as a baseline and a list of improvements, not as a formal accessibility certification.
